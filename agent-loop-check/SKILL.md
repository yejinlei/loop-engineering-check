# Agent Loop + Loop Engineering Check

审计任何 AI Agent 项目，回答一个问题：**面对 LLM 的不确定性，这个项目的 loop 在哪些地方没有设防，一旦模型走偏会怎样？**

## 0. 红线：只读

- 读被审计项目的任何文件；运行只读分析（grep、`python static-hints.py`）。
- **不修改被审计项目的任何文件**。
- 报告只写到审计工作目录（当前目录或用户指定路径），文件名固定 `loop-audit-report.md` + `loop-audit.json`。
- 框架 API 名无法联网核验时**绝不猜**：走自省（第 1 步）拿本机真实签名；自省失败则报告里标注「待确认」并降级证据等级。

---

## 动作 A：审计一个项目

### 第 1 步 · 识别框架（证据优先，不做猜测）

三层证据，按序执行：

| 层 | 手段 | 强度 |
|---|---|---|
| **声明** | `pyproject.toml`、`requirements*.txt`、`poetry.lock`、`uv.lock`、`Pipfile`、`package.json`、`pnpm-lock.yaml` | 中（声明 ≠ 使用） |
| **使用** | 源码 import：`from langgraph` / `import langgraph` / `from google.adk` / `from deepagents` / `from crawl4ai` | 高 |
| **自省** | 本机 introspect 已安装包的真实签名（见下） | 最高（API 名从用户机器抓的，不是从记忆背的） |

**判定规则：声明且被 import，才算「在运行」。只在清单里、源码没 import → 报告记为「未使用」，不参与差异矩阵。**

自省片段（按已识别框架按需运行，任一失败不中断）：

```python
import inspect
try:
    import langgraph.graph as g
    print("langgraph:", inspect.signature(g.StateGraph))
    from langgraph.config import get_config
except Exception as e:
    print("langgraph introspect failed:", e)
try:
    import deepagents
    print("deepagents attrs:", [a for a in dir(deepagents) if not a.startswith('_')])
except Exception as e:
    print("deepagents introspect failed:", e)
try:
    from google.adk.agents import LoopAgent
    print("LoopAgent:", inspect.signature(LoopAgent.__init__))
except Exception as e:
    print("adk introspect failed:", e)
try:
    import crawl4ai
    print("crawl4ai:", getattr(crawl4ai, "__version__", "?"))
except Exception as e:
    print("crawl4ai introspect failed:", e)
```

**四种识别结果，逐一处理：**

| 结果 | 处理 |
|---|---|
| 命中已知框架 | 读 `references/framework-map.md` 里该框架的那一节（该节含差异矩阵 + 自省片段）+ 自省拿真实 API 名 |
| **无框架（自研 loop）** | **跑不变式层全量检查，不做框架映射**。这是主路径，不是例外 |
| 框架不在表内 | 只跑不变式层，显式标记「框架未覆盖，差异层跳过」，提示用「如何新增框架」模板 |
| 项目里根本没有 loop | 报告写「无可检查对象」并给出判定依据，**不误报** |

> 自研 loop（裸 `while` + 直接调 openai/anthropic client）在真实项目中的比例通常**高于**用框架的项目，且没有任何框架兜底。识别到这种情况要当主路径处理，不能当边角案例草草带过。
>
> 「loop」的定义：代码中存在**可重复执行**的结构，其退出依赖 LLM 输出、外部状态或时间条件——典型形态是 while/retry 循环、图编排、递归子 agent 委派。一次性 LLM 调用不是 loop，不需要本审计。

### 第 2 步 · 静态提示扫描（提示，不是判定）

```bash
python scripts/static-hints.py <目标目录> --format json > static-hints.json
```

输出的是**候选证据**（行号 + pattern），供 LLM 语义审计确认或排除。扫描是保守的：一个 pattern 命中 ≠ 违规，LLM 必须去读上下文再判定。禁止在报告里直接引用 pattern 名当作结论。

### 第 3 步 · 逐层检查

**M 层（微观 Agent Loop，框架层）14 项 + L 层（宏观 Loop Engineering）10 项 + 跨层 5 项，全部见下。** 每项都要产出三样东西：`结论（OK / GAP / RISK / N/A / PENDING）` + `证据（file:line 或代码片段）` + `修复建议（具体到改什么）`。

**不要输出「无问题」的项**——无问题占篇幅但不产出信息，只在 JSON 里计数。

**查结论时按三层证据走：**

1. 本文件的不变式表 → 判「缺什么会怎样」。
2. `references/framework-map.md` → 该框架在这一项上的已知行为差异。
3. `references/loop-engineering-patterns.md` → **正向锚点**：判 `GAP`/`RISK` 时，查挂载索引找同类项做得好的真实实现，把「做法 + 迁移要点」写进修复建议；判 `OK` 时用它区分「结构性不可表达」与「运行时检查」（见该文件 §0）。

表格里的 `常见漏点` 列同时包含**负向漏点**（缺它会怎样）与**正向判据**（做得好长什么样），两者用 `→` 分隔。**正向判据是判 `OK` 的准入条件，不是加分项**——只满足负向漏点未犯、但不满足正向判据的，判 `RISK` 而不是 `OK`。

## M 层：微观 Agent Loop（14 项 · 框架层）

| ID | 检查什么 | 常见漏点 |
|---|---|---|
| **M1** | 硬预算熔断：`max_turns` / `max_iterations` / `max_seconds` / `max_tokens` / `max_cost` 是否存在 | 只设了 turns 没设时间；只设了时间没设成本 → **正向判据：预算可以外包，但「谁负责补」必须写得出来**。把限轮外包给上层策略是合法设计选择（deepseek-harness 的 `while (true)` + 自文档「No built-in turn budget, a policy must cancel from `agent/turn-stopping`」就是这种形态），但必须留下两样：扩展点的名字、**目前谁在消费它**。三档分开判——缺失且无人知晓 = `GAP`；缺失但显式文档化并指到扩展点 = `RISK`；计数器存在却没人把它当限用 = 同 M2，`GAP` |
| **M2** | 检查点位置：预算校验在每轮循环**内部**还是只在入口检查一次 | 入口检查一次 = 内部嵌套循环完全不生效 → **正向判据：校验点数量 = 嵌套层级数**。有几层循环就可能耗尽预算，就要有几个校验点。判定时画一遍调用栈：从入口到最深的那层工具调用，每一层「可能自己转很多圈」的位置都要有一次校验。另：**框架自己引起的重试不能占调用方的预算**——OpenHarness 把 `turn_count = max(0, turn_count - 1)` 用于框架侧的重启/自愈重试，即引擎自己触发的重跑不消耗调用方给的轮次。反向形态（框架自愈吃掉调用方的 turns）会让调用方看到「我只跑了两轮」但实际烧了八轮，且这个差额在预算口径上不可见，M1 的计数与实际消耗脱节 |
| **M3** | limiter 计数单位：节点执行次数 / iteration / LLM 调用 / 页面访问 / turn？与「一次 LLM 调用」的换算比是多少？ | 最常漏的一项。单位换算错 = 实际放行了几倍预算。换算比**逐框架不同且不固定**：LangGraph 数 step（一个 superstep 可含多个并行节点）；ADK `max_iterations` 一轮跑完所有子 agent，比是 1:N；Crawl4AI 数页面访问次数。详见 `references/framework-map.md` → **正向判据：换算比要么写进代码里的注释、要么写进配置文档，且能被一个具体数字反查**——「1 轮 = 2 次 LLM 调用」这种换算只有能指到具体行号才算成立，凭直觉的「大概是 1:2」会在子 agent 里变成 1:5。审计动作：拿一个已完成的真实 Run，数一下 limiter 计了多少、实际发生多少次模型调用，两个数不相等且没有文档解释，判 `GAP` |
| **M4** | 超限时行为：硬抛异常 / 静默截断 / 正常返回 / 返回合成结果 | 最危险的不是「静默截断」，而是**框架帮你把结果补齐了**：smolagents 超限会再调一次 LLM 合成一个看起来完整的最终答案，正常返回、不报错。ADK 超限是正常终止，只写 try/except 感知不到。LangGraph 与 OpenAI Agents SDK 则硬抛异常。AutoGen/AG2 未核验，先确认是「正常终止」还是「抛异常」 → **正向判据：超限时要追问「返回的东西从哪来的」**。如果超限时新调一次模型生成最终答案，比静默截断更危险——调用方无从分辨它是真结论还是补出来的 |
| **M5** | 工具幻觉拦截：执行前是否过注册表强校验，未注册工具名一律拒 | LLM 生成的工具名不在白名单里；框架处理分三类——报错（OpenAI SDK 默认 `ModelBehaviorError`）、回传 observation 让模型自愈、静默跳过。**code agent（smolagents）根本没有工具注册表这一层**，检查方法要换成「沙箱是否隔离」 → **正向判据：判的是「校验在调度边界」不是「工具上有校验」**——注册表校验必须发生在 dispatch 分发点（名字查表这一步），而不是分散在各工具自己的定义里；分散式的校验会让漏校验的路径（子 agent 委派、流式续跑、批量执行）成为绕过通道。另：**未注册名字的处置必须是显式的三选一，且三者都产出可观测结果**——报错 / 回传结构化错误结果让模型自愈（pi 的 `createErrorToolResult`，不抛异常）/ 拒绝并中止，都可以；「静默跳过」不行，它让调用方看到一次成功但什么都没发生。审计动作：搜 dispatch 里的名字查找，确认没有 `.get(name, default)` 这类带默认值的降级 |
| **M6** | 参数类型校验：schema 强校验 + 额外字段 + 缺必填 | ADK 声明式工具在结构上已保证；OpenAI SDK 用 `tool(func)` 时 schema 从注解推导，**没注解就是无校验**——这是最常见的漏点。AutoGen/AG2 的推导方式未核验，自省确认后再判 → **正向判据：「查缺必填」不等于「查类型对」**。只校验 required 是否缺失的防线仍会让错误类型执行下去；额外字段被静默丢弃同样是缺陷——模型以为传了，函数没收到 |
| **M7** | 工具调用 JSON 结构：流式响应中工具调用参数未完结就被截断执行 / 缺必填字段就调用 | 拼接流式分片时只检查了文本完整性，没检查 tool_call 的 `arguments` 是否闭合 → **正向判据：三档问，答「有」而第三档答「没有」就是最坏形态**——(1) 有没有「解析失败就换默认值」的分支？JSON 截断换成空字典后工具照跑、Run 照继续、结果照错、无人知晓；(2) 有没有**抢救式解析器**把残缺输入变成合法输入？有它时截断的参数**能通过 schema 校验**，所有防线全绿但拦不住任何东西，这档比第 (1) 档更难发现；(3) 截断信号（`stop_reason: length` / `finish_reason: length`）参与决策了吗？只有这个信号能区分「校验通过的截断调用」和「真的完整的调用」，所以单点修复不够，必须整批失败——同一消息里的调用共享同一个截断点。危险从来不在于「出错」，在于「出错后仍然成功返回」 |
| **M8** | 工具执行失败回传：错误是否进入 observation？失败是否触发重试死循环？ | 失败被吞掉 → agent 以为成功 → 基于错误状态继续；失败全量重试 → 死循环 → **正向判据：两级错误策略要落到 lint 配置才算成立**（观察通道可 `except: continue`，执行通道必须转成结构化失败）。只写在文档里不算策略——下一个贡献者会用 `except Exception: return None` 把失败吞掉 |
| **M9** | 上下文与状态完整性：单轮上下文膨胀、历史污染、并发写入 reducer 覆盖 | LangGraph 的 reducer 坑**会抛异常而不是静默丢状态**（`INVALID_CONCURRENT_GRAPH_UPDATE`）——故障是可用性问题，不是正确性问题；真正的静默风险在「无 reducer 的默认 channel 是覆盖语义，单节点写会无声覆盖」。LlamaIndex 既不是 reducer 也不是 ContextManager，M9 的检查方法要换。AutoGen/AG2 的共享对话历史形态未核验（AG2 主分支已把 GroupChat 迁到 `network` 抽象），检查方法待补 → **正向判据：判 `OK` 前先分清是结构性防线还是检查型防线**（详见 `references/loop-engineering-patterns.md` §0）——检查型防线要追加一问「覆盖了几条分支？」，答不清降级 `RISK`。三条具体锚点：① **多写点的键要声明合并规则**，让并发歧义在构造期就无法表达，而不是运行期抛异常；② **上下文裁剪按原子组**——按「调用 + 其结果」成组整组丢弃，绝不留孤儿工具结果（模型看到无主结果会直接报错）；③ **压缩要分级，机械手段优先于花模型的钱**，且级别选择要有可观测输出；文本截断要写出省略了多少字符，无声截断会让模型基于残缺信息作答 |
| **M10** | 部分输出与流式完整性：半截响应、`stop_reason` / `finish_reason` 检查、token 计数口径 | 只检查了「有返回」，没检查「返回是否完整」 → **正向判据：流式失败要响亮且带原始证据**——空响应时抛异常并在错误信息里保留若干原始分片，才能定位根因。同一份代码里若存在「解析失败就换默认值」的静默分支，就是 M10 与 M7 复合的最坏形态 |
| **M11** | 错误恢复与可重试性：幂等性、可重试 vs 不可重试错误分类 | 把 4xx（不可重试）当 5xx（可重试）重试，或反之 → **正向判据：分类逻辑要可替换**（谓词或策略对象，不是硬编码 if-else）——用户换分类不该改引擎。**两条追加判据**：(a) **同批调用里出现分歧时怎么归约？** 一个消息发出多个工具调用，其中几个该终止、几个不该终止——多数决、首个胜出、还是全批一致？只有「全批一致才终止」是安全选择：取多数等于让少数服从错误，取首个等于把顺序当语义。这一项和 M7 是同一枚硬币：M7 说截断要整批失败（同批共享截断点），M11 说终止也要整批判定（同批共享一个控制流决定）。(b) **幂等性要说清是「同参数」幂等还是「同意图」幂等**——前者靠参数哈希就能查，后者必须靠语义键，两者不可互替 |
| **M12** | 输出契约校验：响应是否通过结构化 schema 校验 | agent 自由文本输出直接喂给下游解析，解析失败静默降级 → **正向判据：「解析失败怎么办」必须是三个可区分分支**——重试、升级为失败、还是降级？降级时有没有发出「已经降级」的可观测信号？没有信号的静默降级把契约违约变成了成功返回，和 M7/M10 是同一类形态。**另要问判据本身可判定吗**：如果「是否符合契约」由模型自判（自评输出是否合格），就退化成「让作者批改自己的作业」，这条防线没有强制力，等同 X3 的交接条件由模型自判 |
| **M13** | 安全护栏：prompt injection（内容来自外部/爬取）、输出泄露、PII 处理、工具权限边界 | 爬取内容直接进 prompt 无净化；工具无权限分级，低权限 agent 可触达高权限工具 → **正向判据：「有分类」不等于「覆盖完整」，三步问**——(1) 分类有哪些取值？(2) **哪些代码路径跳过分类、走了默认值？**（委派工具、外部/MCP 工具被硬编码成只读是两条经典旁路）(3) 默认值在权限模型里代表什么？只要存在走默认值的路径，判 `RISK` 而非 `OK`。另：**审批必须 fail-closed**——观察通道的容错（错误隔离、静默降级）用在准入通道上，等于「审批服务挂了 = 全部放行」。**第三条问：这条防线能不能物理阻止被禁止的动作？** 建议性约束（提醒、协作式超时、注入上下文让模型自己改）降低失败概率，但不让失败不可能。deepseek-harness 的 `packages/guard/` 全线自述为 advisory——`timeout-policy` 是「Cooperative, never a hard kill」，且内建的 `bash`/`read`/`write`/`edit` 均未声明 `timeoutMs`，即**默认无时限**；`repeat-tool-reminder` 是「Advisory, not veto. It never blocks or rewrites a call.」它的强制层是另一个独立包（`interaction/user-approval/`，fail-closed）。准入条件：**唯一的安全边界如果是建议性的，判 `RISK` 而非 `OK`**；同时问「默认配置下强制层启没启用」——需要显式配置且无注册表默认值的护栏，等于没有护栏。**再加一问求值顺序**：存在不可被配置覆盖的硬拒层时，看它排在所有可配置项之前还是之后——`FULL_AUTO`（全放行）分支如果放在敏感路径检查之前，那条硬拒层就形同虚设。求值顺序是实质，不是细节：同样一份名单，顺序错了就从安全边界变成摆设 |
| **M14** | 模型不确定性：随机种子 / 温度是否记录、`temperature>0` 时是否假设了确定性输出 | 温度 0.7 却假设输出可复现 → **正向判据：区分「假设确定性」和「记录不确定性」两个动作**。前者是设计选择，后者是审计义务：哪怕温度非零、注定不可复现，模型名 / 温度 / 采样参数也要落盘——否则出问题时连「当时用的是什么」都答不上来，X2 的可重放无从谈起。审计问法是「这个项目哪一行断言了输出可复现？」（缓存键、去重键、幂等键、结果比对），答不上来但存在这类断言，判 `GAP`；答得上来且参数已记录，判 `OK` |

## L 层：宏观 Loop Engineering（10 项）

| ID | 检查什么 | 常见漏点 |
|---|---|---|
| **L1** | 外层编排循环边界：外层迭代上限 + 明确终止条件 | 外层无上限，靠「模型会自己停」→ **正向判据：终态必须是代码里可区分的三条路径**（正常完成 / 达上限熔断 / 无节点 ready 判为卡住），不能靠一个布尔量事后推断。收缩类逻辑（skip、timeout 收敛）必须有前置条件——只有「本波次真的没人在跑」时才收缩，否则会把等回边的节点误判成死节点。**两条追加判据**：(a) 还要问第四问——如果这个循环**根本没设上限**，退出时能被观测到吗？`while` 理论上永不退出，所以「未达上限就退出」本身是异常事件，必须有它自己的终态名字；混在同一个错误里，修复建议就没法定位（达上限了 = 降轮数；压根没配上限 = M1 的 GAP）。(b) 基于信号/事件唤醒的循环，**唤醒可被丢弃**（非阻塞发送、有界队列溢出）时必须有有限轮询兜底——否则丢信号是活性 bug：任务永远不会被调度且无错误可查。审计时问「唤醒能不能丢」，答「不能丢」但发送是非阻塞的，就是声明与实现不一致 |
| **L2** | 预算下传：总预算是否传递到每个子 Agent？子 Agent 是否独立受限？ | 外层设了上限、内层无上限 = 白设，这是最普遍的宏观漏洞。**但「是否继承」逐框架不同**：OpenAI Agents SDK 的 handoff 共享 run 级 `max_turns`（继承成立）；LangGraph 子图需显式传递；ADK 的 `max_iterations` 只管 LoopAgent 自己的迭代、子 agent 终止靠各自的 `tool_context.actions.escalate` → **正向判据：要有 Run 树级的聚合预算**，而不只是每层各自的局部上限。局部上限之和没有上界时，深度守卫再严也拦不住烧钱。另：**除了问「有没有下传」，还要问「每一条构造路径都接上了吗」**——上层包装器构造引擎时漏传上限参数、落回默认值，是这道检查最容易漏掉的形态：它不是「配置错了」，是那条路径**根本没接到配置**，所以配置审计看不出来 |
| **L3** | 委派深度与广度：递归深度上限 + 每层子 Agent 数量上限 | 子 agent 递归调用子 agent，深度无界 → **正向判据：深度与广度必须分别问、分别判**。深度有守卫不等于 L3 通过——一次 fan-out 一万个副本，一万个节点同一波次 ready、每个各调一次模型，深度有界而广度无界。广度上限缺失时的正确修法是**抛异常而不是截断**（截断 = 静默丢任务）。另：**并发与限流守卫要排除「已经在跑的工作」与「自身」**——harness/harness 的 `withinLimits` 显式排除了其他仓库、自己、其他名字，`shouldThrottle` 对 `CIStatusRunning` 直接返回 false。这两处排除不是巧合：守卫如果追溯已在执行的任务，就是自我锁死；如果把自己算进计数，一次调度就会把自己限流掉。审计并发守卫时问「这个计数里包不包括当前这次？」，答「包括」就要判 `RISK` |
| **L4** | 外层决策可判定性：continue / retry / fix / escalate 四态是否都是可机器判定的条件 | 「决定继续」依赖模型自判 → 无法收敛 → **正向判据：分支条件必须是可机器判定的**；必须由模型判定的（如「是否达成共识」）要显式标出来并单独判 `RISK`。另：**回到某个节点的操作必须显式区分「立即释放」与「等入边就绪」**——迭代收敛点用立即释放会读到空状态，然后「合成了一个空结果」，这是不报错的错误 |
| **L5** | 检查点与恢复：状态快照是否存在？恢复时不丢状态、不重复副作用 | 有检查点但恢复会重放已完成的副作用（重复下单、重复发送）→ **正向判据：检查点对象里不能有活对象**（client、session、connection）。把「连线」和「数据」拆成两个类型，检查点自动变干净；混在一起时靠序列化白名单是漏的。**三条追加判据**：(a) **收尾路径不能继承触发它的那个取消令牌**——取消流程本身是被取消的那个操作的一部分，如果收尾绑定同一个 ctx，被取消的操作连自己的清理都做不完（harness/harness 的 teardown 对所有存储 I/O 用 `noContext`，只在下游调度/取消/上报用 ctx，就是这个理由）。(b) **检查点要显式记录「续跑什么」，而不只是「跑到哪」**——pi 的 checkpoint 带 `continuation: { kind: "need_assistant", overflowRecoveryUsed: false }` 与 `triggerEntryId`，恢复时是 `kind: "resume_checkpoint"`。只存状态不存意图，恢复方就得猜下一步，猜错是无声的。(c) **检查点必须是操作（状态转移），不是对象**——pi 的 `CheckpointOperation` 是带 `at: "checkpoint"` 的日志条目，落进 session 日志本身，所以检查点是事件溯源的一部分，不是旁路的对象存储 |
| **L6** | 副作用幂等与去重：外部副作用（支付、发消息、写库）是否有幂等键 | L5 恢复 / L7 重试触发重复副作用 → **正向判据：三步问，三步都答得上才算 `OK`**——(1) 有没有键？(2) **键的粒度是操作级还是更粗？**（节点级/attempt 级的键会让同一波内的多个调用碰撞）(3) 谁在读这个键、有没有强制去重？只答上第 (1) 步是最常见的误判：键存在、被文档化了、但会碰撞且无人强制，比没有键更危险——错误的去重让操作**静默丢失**而不是报错。**两条追加判据**：(a) **部分失败必须编码进数据，不能只进日志**——harness/harness 的 teardown 把 sibling 状态折成 execution 状态（Killed → Failure → Error，首个匹配胜出），取消器给被杀的 step 写 `ExitCode = 130`、给未启动的写 `Skipped`。日志里写「有个 step 失败了」对下游没用，下游要读到的是「这个 step 从来没跑过」。(b) **终态要能区分「启动后被杀」和「从未启动」**——同一个 `Failed` 覆盖两种情况，下游就没法判断要不要重跑（重跑已跑过的 = 重复副作用；不重跑没跑过的 = 任务丢失）。这个区分比幂等键更靠前，因为幂等键只在「会重跑」时才起作用 |
| **L7** | 失败收敛策略：换参数 / 换 agent / 升级人工 / fail-fast 的路径是否定义 | 只有「再试一次」，没有「试到第几次做什么」→ **正向判据：两级错误策略，按「谁能修好它」分类**——模型能修的（缺参数、工具抛异常）转成数据回传给模型；模型修不了的（结构性错误）必须 fail-fast 并响亮。分类依据**不能是异常类型**（`ValueError` 有时该重试有时不该）。配套：**超限绝不合成答案**，宁可直接失败也不产出「看起来完成」的东西 |
| **L8** | 重试策略与退避：即时重试 vs backoff + jitter；重试是否换了参数 | 相同输入即时重试 = 同样地失败 N 次，纯烧钱 → **正向判据：五问，缺一问就不能判 `OK`**——(1) 有没有最大重试次数？(2) **可重试错误码是不是白名单**（不是 `except Exception`）？(3) 延迟有没有上限？(4) 有没有 jitter？(5) jitter 是乘性对称还是加性？（纯指数无 jitter 会让并发重试同步齐步，形成 thundering herd）另有三条硬要求：**重试判据要可替换**（谓词或策略对象，不是硬编码 if-else）；**默认值必须保守**——`retry_on=(Exception,)` 这种默认把「重试策略」变成了「所有错误都重试」，会把程序 bug 也重试掉；**指数要防溢出**（`2 ** retry` 在 `retry` 极大时会让延迟算成天文数字）。机制和默认值**必须一起判**：策略对象设计得再好，默认 `retry_on=(Exception,)` 仍然零分（案例 1 的形态）；反之默认值有上限但判据硬编码，用户无法收窄重试范围。**两条来自上游的追加判据**：(a) **双正则分类时，非重试的必须在重试的之前测**——pi 先测 `NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN` 再测 `RETRYABLE_PROVIDER_ERROR_PATTERN`。反向顺序时，一个同时匹配两者的错误串（限流消息里常常含 retry 字样）会被判成可重试，限流就被重试探满预算。(b) **溢出要防两层，不是两层里挑一层**——JS 里 `Number.isSafeInteger` 兜的是数值精度，`setTimeout` 的 32 位上限要单独 `Math.min(remaining, 2_147_483_647)`。只防其一的形态：延迟算出来正确但 `setTimeout` 拿到天文数字直接静默不触发，重试永远不回来 |
| **L9** | 跨 Agent 结果一致性：冲突检测 + 事实单一来源 | 两个子 agent 给出矛盾结论，外层直接拼接 → **正向判据：先问「有没有一个字段是事实唯一来源」**。有唯一来源时，其他 agent 的结论只是引用而非新增事实，冲突在构造期就不可能出现。没有唯一来源就要问冲突怎么发现——拼接式合成（把两份结论写进同一个回复）不产生任何可检测的冲突信号，它只是让两个矛盾事实同时为真。判定条件：**如果两份结论互相矛盾，代码里有没有一个分支会因为这个矛盾而停下来？** 答不上来判 `GAP`。注意这不是「加个 LLM 去比对」——让模型判冲突又退回到 M12 那个「让作者批改自己的作业」形态 |
| **L10** | 验收与 Goodhart 防护：done 判据 + 边界条件（「不许做什么」），验收器不可被被优化对象修改 | 只用「所有测试通过」做出口 → agent 删测试就赢了 → **正向判据：fail-fast 之外还要有「挂起等人工」这条路**。重试耗尽后当前只能抛异常，等于「要么无限重试要么直接死」，缺了中间那档。**Goodhart 的具体形态：验收器在「证据缺失」时判过**。OpenHarness 的 `_wait_for_pr_ci` 在 `no_checks_grace_seconds` 之后如果仍然没有收到任何 remote check，返回 `("success", "No remote checks were reported after the grace period.")`——验收器在检查项根本不存在时给出通过结论。审计验收逻辑时必须问「没有证据时算什么结果？」，答「超时算通过」就是这一档。同构形态还有：检查项集合为空 → 判全绿；验收脚本自己被删 → 判没有失败项。这类缺陷比「验收标准太松」更隐蔽，因为它有完整的超时、优雅等待、快照机制，看上去是严谨的实现 |

## 跨层（5 项）

| ID | 检查什么 | 漏点 |
|---|---|---|
| **X1** | 可观测性：每次迭代是否有结构化日志（迭代号、成本、决策、工具调用、错误） | 只有最终结果日志，中间决策链不可追溯 → **正向判据：日志要能回答「这次花了多少」和「哪个工具调用坏的」**。事件里有重试次数、延迟、错误类型但没有成本、token、工具名与参数时，仍然无法定位根因——重试元数据不是成本观测 |
| **X2** | 可重放：随机种子 / 时间戳 / 外部响应是否被记录 | 出问题后无法复现 → **正向判据：区分「能重建状态」和「能重建运行」**。事件溯源存波次 delta 只能重建状态；模型的回复、模型名、温度没记录时，重放走一遍是另一条路径。这个区别在报告中要写明 |
| **X3** | 人机交接：升级人工的条件是否明确定义？交接信息是否完整？ | 无人工交接路径，或条件模糊（「模型不确定时」） → **正向判据：交接条件要机器可判定**。「何时问人」如果由模型自判，交接点就等于随机数；恢复时输入的形态（字典 vs 裸值）要有明确契约，靠启发式消歧是缺陷 |
| **X4** | 环境一致性：dev / staging / prod 的 loop 配置（上限、超时、模型）是否有差异 | 本地无限循环跑着挺好，生产有上限直接截断 → **正向判据：上限的缺失必须显式声明，且方向要单一反查得出来**。判定的核心不是「两个环境配置一样」，而是「哪个环境少了哪个上限」能在一处查出来：环境间差异表、或被引用的单一配置源。若每个环境各写一份完整配置，多出的那份永远不会被删，删的那份也无人知晓。审计问法：**把三个环境的上限配置并排，哪个环境在这一项上是空的？** 答不上来（因为差异分散在各处文件里）就是 `GAP`——X5 的空行在这里是配置层，在 X4 是环境层，两个都要判 |
| **X5** | 配置漂移：默认值是否静默失效？配置项拼错是否有警告？ | 配置 key 拼错一个字母 → 静默回落到无上限默认值 → **正向判据：枚举配置与数字配置分开判**。枚举做白名单校验（拼错即抛异常、错误信息带拼错的值）成本最低收益最高；数字配置要单独问有没有下限检查——`concurrency=0` 会让信号量永久锁死且无异常无日志，`max_waves=-1` 意味着完全无上限。一个项目可以在枚举上满分、在数字上零分。**三类校验分开问**：(1) 拼错的 key 会不会抛？(2) 数字越界会不会抛？(3) **字段之间有没有关系需要校验？** 第三类最容易漏——`headChars=5000`、`tailChars=4000`、`thresholdChars=8192` 三个值各自合法，加起来却超过阈值，裁剪器要么死循环要么输出比原文更长。跨字段不变量必须**在构造期**校验，留给运行期就是「出错后仍然成功返回」。deepseek-harness 的 pruner 这条校验写成了 `headChars + codePointLength(MARKER) + tailChars <= thresholdChars`，并且把解析出的配置 `deepFreeze(structuredClone(...))` 成深层不可变——**配置对象可变时，构造期校验等于没校验** |

**第四类：配置是合并还是整体替换？** 整体替换语义下，patch 作者漏写一个字段得到的是**默认值**而不是旧值。如果默认值恰好是无上限（deepseek-harness 的 `retry-policy` 省略即取 normal 默认 5 次重试，而 `always` 模式的 provider 省略即无重试上限），patch 会**静默移除**一条安全限制，且配置审计看不出来——这是「边界不可发现」在配置层的形态。审计分层配置时先问合并语义，再问漏写会发生什么。

**第五类：钳制必须可观测，且枚举值与数字值分开钳。** OpenHarness 的 `_safe_completion_token_cap` 对超限值做钳制后会通过 `StatusEvent` 报出「钳制了什么、钳到多少」。无声钳制让调用方以为配的是 20000、实际跑的是 8192，配置审计与运行行为长期不一致且无从发现。同时枚举型字段（如压缩级别）走白名单校验、数字型字段走范围钳制，两者不能共用一套处理，否则「拼错的枚举」会被当成越界数字静默回落到默认。
