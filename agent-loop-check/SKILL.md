# Agent Loop + Loop Engineering Check

审计任何 AI Agent 项目，回答一个问题：**面对 LLM 的不确定性，这个项目的 loop 在哪些地方没有设防，一旦模型走偏会怎样？**

## 0. 红线：只读

- 读被审计项目的任何文件；运行只读分析（grep、`python static-hints.py`）。
- **不修改被审计项目的任何文件**。
- 报告只写到审计工作目录（当前目录或用户指定路径），文件名固定 `loop-audit-report.md` + `loop-audit.json`。
- 框架 API 名无法联网核验时**绝不猜**：走自省（第 1 步）拿本机真实签名；自省失败则报告里标注「待确认」并降级证据等级。

## 动作 A：审计一个项目

### 第 1 步 · 识别框架（证据优先，不做猜测）

三层证据，按序执行：

| 层 | 手段 | 强度 |
|---|---|---|
| **声明** | `pyproject.toml`、`requirements*.txt`、`poetry.lock`、`uv.lock`、`Pipfile`、`package.json`、`pnpm-lock.yaml` | 中（声明 ≠ 使用） |
| **使用** | 源码 import：`from langgraph` / `import langgraph` / `from google.adk` / `from deepagents` / `from crawl4ai` | 高 |
| **自省** | 本机 introspect 已安装包的真实签名（见下） | 最高（API 名从用户机器抓的，不是从记忆背的） |

**判定规则：声明且被 import，才算「在运行」。只在清单里、源码没 import → 报告记为「未使用」，不参与差异矩阵。**

自省片段（按已识别框架按需运行，任一失败不中断）：

```python
import inspect
try:
    import langgraph.graph as g
    print("langgraph:", inspect.signature(g.StateGraph))
    from langgraph.config import get_config
except Exception as e:
    print("langgraph introspect failed:", e)
try:
    import deepagents
    print("deepagents attrs:", [a for a in dir(deepagents) if not a.startswith('_')])
except Exception as e:
    print("deepagents introspect failed:", e)
try:
    from google.adk.agents import LoopAgent
    print("LoopAgent:", inspect.signature(LoopAgent.__init__))
except Exception as e:
    print("adk introspect failed:", e)
try:
    import crawl4ai
    print("crawl4ai:", getattr(crawl4ai, "__version__", "?"))
except Exception as e:
    print("crawl4ai introspect failed:", e)
```

**四种识别结果，逐一处理：**

| 结果 | 处理 |
|---|---|
| 命中已知框架 | 读 `references/framework-map.md` 里该框架的那一节（该节含差异矩阵 + 自省片段）+ 自省拿真实 API 名 |
| **无框架（自研 loop）** | **跑不变式层全量检查，不做框架映射**。这是主路径，不是例外 |
| 框架不在表内 | 只跑不变式层，显式标记「框架未覆盖，差异层跳过」，提示用「如何新增框架」模板 |
| 项目里根本没有 loop | 报告写「无可检查对象」并给出判定依据，**不误报** |

> 自研 loop（裸 `while` + 直接调 openai/anthropic client）在真实项目中的比例通常**高于**用框架的项目，且没有任何框架兜底。识别到这种情况要当主路径处理，不能当边角案例草草带过。
>
> 「loop」的定义：代码中存在**可重复执行**的结构，其退出依赖 LLM 输出、外部状态或时间条件——典型形态是 while/retry 循环、图编排、递归子 agent 委派。一次性 LLM 调用不是 loop，不需要本审计。

### 第 2 步 · 静态提示扫描（提示，不是判定）

```bash
python scripts/static-hints.py <目标目录> --format json > static-hints.json
```

输出的是**候选证据**（行号 + pattern），供 LLM 语义审计确认或排除。扫描是保守的：一个 pattern 命中 ≠ 违规，LLM 必须去读上下文再判定。禁止在报告里直接引用 pattern 名当作结论。

### 第 3 步 · 逐层检查

**M 层（微观 Agent Loop，框架层）14 项 + L 层（宏观 Loop Engineering）10 项 + 跨层 5 项，全部见下。** 每项都要产出三样东西：`结论（OK / GAP / RISK / N/A / PENDING）` + `证据（file:line 或代码片段）` + `修复建议（具体到改什么）`。

**不要输出「无问题」的项**——无问题占篇幅但不产出信息，只在 JSON 里计数。

**查结论时按三层证据走：**

1. 本文件的不变式表 → 判「缺什么会怎样」。
2. `references/framework-map.md` → 该框架在这一项上的已知行为差异。
3. `references/loop-engineering-patterns.md` → **正向锚点**：判 `GAP`/`RISK` 时，查挂载索引找同类项做得好的真实实现，把「做法 + 迁移要点」写进修复建议；判 `OK` 时用它区分「结构性不可表达」与「运行时检查」（见该文件 §0）。

表格里的 `常见漏点` 列同时包含**负向漏点**（缺它会怎样）与**正向判据**（做得好长什么样），两者用 `→` 分隔。**正向判据是判 `OK` 的准入条件，不是加分项**——只满足负向漏点未犯、但不满足正向判据的，判 `RISK` 而不是 `OK`。

## M 层：微观 Agent Loop（14 项 · 框架层）

| ID | 检查什么 | 常见漏点 |
|---|---|---|
| **M1** | 硬预算熔断：`max_turns` / `max_iterations` / `max_seconds` / `max_tokens` / `max_cost` 是否存在 | 只设了 turns 没设时间；只设了时间没设成本 → **正向判据：预算可以外包，但「谁负责补」必须写得出来**。把限轮外包给上层策略是合法设计选择（deepseek-harness 的 `while (true)` + 自文档「No built-in turn budget, a policy must cancel from `agent/turn-stopping`」就是这种形态），但必须留下两样：扩展点的名字、**目前谁在消费它**。三档分开判——缺失且无人知晓 = `GAP`；缺失但显式文档化并指到扩展点 = `RISK`；计数器存在却没人把它当限用 = 同 M2，`GAP`。**第四条：重试预算要乘上单次尝试成本**——重试次数是预算，单次尝试成本是价格，两者相乘才是花费。单次成本已经很高时，继续重试只是烧钱而不改善结果，此时预算应该收缩。判据要落到数字：单次估算成本超过阈值时预算从 N 降到 M，N 与 M 都要写出来。hermes-agent 的 `empty_response_guard` 就是这个交叉点：单次空响应估算输入成本超过阈值（默认 `$0.25`）时，空响应重试预算从 3 降到 1，且未知定价/缺失 usage 时预算不动（不动的方向也是判据——见 X5 第六类）。**第五条：预算的豁免通道必须在本模块内可审计**——如果循环条件里引用了一个本模块从不写入的状态作为豁免项（hermes-agent 的 `agent._budget_grace_call` 只出现在循环条件里，授权点不在 loop 自己的源码中），审计者无法判断这个豁免谁能开、开了多久；这种形态比缺守卫更难审计，因为缺守卫是明面上的缺口、不可审计的豁免是看不见的缺口（判据全文见 `references/loop-engineering-patterns.md` 模式 53，该反例同时挂在 L1） |
| **M2** | 检查点位置：预算校验在每轮循环**内部**还是只在入口检查一次 | 入口检查一次 = 内部嵌套循环完全不生效 → **正向判据：校验点数量 = 嵌套层级数**。有几层循环就可能耗尽预算，就要有几个校验点。判定时画一遍调用栈：从入口到最深的那层工具调用，每一层「可能自己转很多圈」的位置都要有一次校验。另：**框架自己引起的重试不能占调用方的预算**——OpenHarness 把 `turn_count = max(0, turn_count - 1)` 用于框架侧的重启/自愈重试，即引擎自己触发的重跑不消耗调用方给的轮次。反向形态（框架自愈吃掉调用方的 turns）会让调用方看到「我只跑了两轮」但实际烧了八轮，且这个差额在预算口径上不可见，M1 的计数与实际消耗脱节 |
| **M3** | limiter 计数单位：节点执行次数 / iteration / LLM 调用 / 页面访问 / turn？与「一次 LLM 调用」的换算比是多少？ | 最常漏的一项。单位换算错 = 实际放行了几倍预算。换算比**逐框架不同且不固定**：LangGraph 数 step（一个 superstep 可含多个并行节点）；ADK `max_iterations` 一轮跑完所有子 agent，比是 1:N；Crawl4AI 数页面访问次数。详见 `references/framework-map.md` → **正向判据：换算比要么写进代码里的注释、要么写进配置文档，且能被一个具体数字反查**——「1 轮 = 2 次 LLM 调用」这种换算只有能指到具体行号才算成立，凭直觉的「大概是 1:2」会在子 agent 里变成 1:5。审计动作：拿一个已完成的真实 Run，数一下 limiter 计了多少、实际发生多少次模型调用，两个数不相等且没有文档解释，判 `GAP` |
| **M4** | 超限时行为：硬抛异常 / 静默截断 / 正常返回 / 返回合成结果 | 最危险的不是「静默截断」，而是**框架帮你把结果补齐了**：smolagents 超限会再调一次 LLM 合成一个看起来完整的最终答案，正常返回、不报错。ADK 超限是正常终止，只写 try/except 感知不到。LangGraph 与 OpenAI Agents SDK 则硬抛异常。AutoGen/AG2 未核验，先确认是「正常终止」还是「抛异常」 → **正向判据：超限时要追问「返回的东西从哪来的」**。如果超限时新调一次模型生成最终答案，比静默截断更危险——调用方无从分辨它是真结论还是补出来的 |
| **M5** | 工具幻觉拦截：执行前是否过注册表强校验，未注册工具名一律拒 | LLM 生成的工具名不在白名单里；框架处理分三类——报错（OpenAI SDK 默认 `ModelBehaviorError`）、回传 observation 让模型自愈、静默跳过。**code agent（smolagents）根本没有工具注册表这一层**，检查方法要换成「沙箱是否隔离」 → **正向判据：判的是「校验在调度边界」不是「工具上有校验」**——注册表校验必须发生在 dispatch 分发点（名字查表这一步），而不是分散在各工具自己的定义里；分散式的校验会让漏校验的路径（子 agent 委派、流式续跑、批量执行）成为绕过通道。另：**未注册名字的处置必须是显式的三选一，且三者都产出可观测结果**——报错 / 回传结构化错误结果让模型自愈（pi 的 `createErrorToolResult`，不抛异常）/ 拒绝并中止，都可以；「静默跳过」不行，它让调用方看到一次成功但什么都没发生。审计动作：搜 dispatch 里的名字查找，确认没有 `.get(name, default)` 这类带默认值的降级。**混合批（同一消息里既有合法名字又有非法名字）要单独问**：整批判废、还是只对非法调用返回错误结果并照跑合法调用？两者都可以，但整批判废会丢弃模型已经做对的那部分工作，而只对非法调用报错能让模型自己纠正。选后者时有一个**必须配套的约束**：「打击次数」的推进条件要看整批——hermes-agent 的 `_invalid_tool_retries` 只在整批**没有任何**有效调用时才递增，混合批则把它清零。漏掉这条配套约束的后果是具体的：一个退化模型只要每批恰好带一个有效调用，打击次数就永远到不了上限，3 击熔断形同虚设。这条和 M11 的「全批一致才终止」是同一个不变式的两面：判定看整批，计数也要看整批 |
| **M6** | 参数类型校验：schema 强校验 + 额外字段 + 缺必填 | ADK 声明式工具在结构上已保证；OpenAI SDK 用 `tool(func)` 时 schema 从注解推导，**没注解就是无校验**——这是最常见的漏点。AutoGen/AG2 的推导方式未核验，自省确认后再判 → **正向判据：「查缺必填」不等于「查类型对」**。只校验 required 是否缺失的防线仍会让错误类型执行下去；额外字段被静默丢弃同样是缺陷——模型以为传了，函数没收到 |
| **M7** | 工具调用 JSON 结构：流式响应中工具调用参数未完结就被截断执行 / 缺必填字段就调用 | 拼接流式分片时只检查了文本完整性，没检查 tool_call 的 `arguments` 是否闭合 → **正向判据：三档问，答「有」而第三档答「没有」就是最坏形态**——(1) 有没有「解析失败就换默认值」的分支？JSON 截断换成空字典后工具照跑、Run 照继续、结果照错、无人知晓；(2) 有没有**抢救式解析器**把残缺输入变成合法输入？有它时截断的参数**能通过 schema 校验**，所有防线全绿但拦不住任何东西，这档比第 (1) 档更难发现；(3) 截断信号（`stop_reason: length` / `finish_reason: length`）参与决策了吗？只有这个信号能区分「校验通过的截断调用」和「真的完整的调用」，所以单点修复不够，必须整批失败——同一消息里的调用共享同一个截断点。危险从来不在于「出错」，在于「出错后仍然成功返回」。**三条追加判据**：(a) **截断后的重试预算要按「截断类型」分开**——文本截断的重试与工具调用截断的重试是两个独立计数器，各自有各自的上限；共用一个计数器会让其中一类把另一类的预算吃光。(b) **工具调用被截断后的重试要同时抬高单次输出上限**——如果截断的原因是模型真的用满了输出预算，不抬高上限的重试只会再次截断，把同一个错犯 N 次；抬高要设封顶，抬高倍数要可审计。(c) **重试用尽后要回答「这个动作执行了没」**——参数残缺的调用重试到上限后必须中止并明确报告「未执行」，不能执行残缺参数、也不能让残缺调用落进下一轮被当成有效调用：那把「没执行」伪装成了「执行了但结果不对」，和上面「出错后仍然成功返回」是同一形态，只是发生在下一轮 |
| **M8** | 工具执行失败回传：错误是否进入 observation？失败是否触发重试死循环？ | 失败被吞掉 → agent 以为成功 → 基于错误状态继续；失败全量重试 → 死循环 → **正向判据：两级错误策略要落到 lint 配置才算成立**（观察通道可 `except: continue`，执行通道必须转成结构化失败）。只写在文档里不算策略——下一个贡献者会用 `except Exception: return None` 把失败吞掉 |
| **M9** | 上下文与状态完整性：单轮上下文膨胀、历史污染、并发写入 reducer 覆盖 | LangGraph 的 reducer 坑**会抛异常而不是静默丢状态**（`INVALID_CONCURRENT_GRAPH_UPDATE`）——故障是可用性问题，不是正确性问题；真正的静默风险在「无 reducer 的默认 channel 是覆盖语义，单节点写会无声覆盖」。LlamaIndex 既不是 reducer 也不是 ContextManager，M9 的检查方法要换。AutoGen/AG2 的共享对话历史形态未核验（AG2 主分支已把 GroupChat 迁到 `network` 抽象），检查方法待补 → **正向判据：判 `OK` 前先分清是结构性防线还是检查型防线**（详见 `references/loop-engineering-patterns.md` §0）——检查型防线要追加一问「覆盖了几条分支？」，答不清降级 `RISK`。三条具体锚点：① **多写点的键要声明合并规则**，让并发歧义在构造期就无法表达，而不是运行期抛异常；② **上下文裁剪按原子组**——按「调用 + 其结果」成组整组丢弃，绝不留孤儿工具结果（模型看到无主结果会直接报错）；③ **压缩要分级，机械手段优先于花模型的钱**，且级别选择要有可观测输出；文本截断要写出省略了多少字符，无声截断会让模型基于残缺信息作答；④ **交接给下游模块的字段清单要从接收方自己的声明派生，不要手写枚举**——hermes-agent 的主循环把状态交给 finalizer 时用 `inspect.signature(finalize_turn).parameters` 过滤出参数名再逐个 `getattr` 取，字段清单随接收方签名自动增长。手写枚举的清单漏一个字段不报错，下游拿到 `None` 后照常跑完，「状态没传过去」被当成「这个字段本来就空」；派生式的清单让「接收方加了参数」这一动作本身成为唯一改动点，漏传在结构上不可能；⑤ **状态的清零责任归消费方，不归记录方**——hermes-agent 的 `record_empty_attempt` 在记录一次空响应时检查「计数器是否为 0」，是则清空历史并归零累计成本，注释写明「cleared whenever `_empty_content_retries == 0` at record time, so every existing counter-reset site (turn start, compaction, tool success, fallback activation) is honoured」。维护一份「所有该清零的地方」的清单必然漏（新增一个重置点时没人改护栏），把清零归约成消费方的单一判据则新增重置点不需要改任何护栏代码。判据：**能指出这一个判据吗？还是有一处维护中的重置点清单？** 后者每加一个状态源就多一个漏配风险。同时注意顺序约束：记录必须在递增之前发生，否则计数器永远不为 0，判据永远不触发，护栏静默失效 |
| **M10** | 部分输出与流式完整性：半截响应、`stop_reason` / `finish_reason` 检查、token 计数口径 | 只检查了「有返回」，没检查「返回是否完整」 → **正向判据：流式失败要响亮且带原始证据**——空响应时抛异常并在错误信息里保留若干原始分片，才能定位根因。同一份代码里若存在「解析失败就换默认值」的静默分支，就是 M10 与 M7 复合的最坏形态。**续跑路径自身是独立的失败模式，且拦截点要在续跑之前**——`finish_reason: length` 触发的续跑会反复拼出退化输出：如果续跑后模型又产出同样长度的输出，续跑一路续到上限，「一次没写完」变成「N 次都没写完」，最终交付一份拼起来的退化文本。hermes-agent 记录过的一次真实事故是一个 60k 字符回合被切成 31 条消息发出，它的拦截点在**续跑路径之前**（重复检测在续跑决策前生效，而不是让续跑再跑几轮）。判据要问续跑耗尽后交付的是哪种：**原样截断的部分结果 + 明确标注 `partial`**，还是**拼起来看起来完整的退化文本**——后者让调用方以为拿到了完整结论，与 M7 的「出错后仍然成功返回」同构，只是发生在续跑这条路上 |
| **M11** | 错误恢复与可重试性：幂等性、可重试 vs 不可重试错误分类 | 把 4xx（不可重试）当 5xx（可重试）重试，或反之 → **正向判据：分类逻辑要可替换**（谓词或策略对象，不是硬编码 if-else）——用户换分类不该改引擎。**两条追加判据**：(a) **同批调用里出现分歧时怎么归约？** 一个消息发出多个工具调用，其中几个该终止、几个不该终止——多数决、首个胜出、还是全批一致？只有「全批一致才终止」是安全选择：取多数等于让少数服从错误，取首个等于把顺序当语义。这一项和 M7 是同一枚硬币：M7 说截断要整批失败（同批共享截断点），M11 说终止也要整批判定（同批共享一个控制流决定）。(b) **幂等性要说清是「同参数」幂等还是「同意图」幂等**——前者靠参数哈希就能查，后者必须靠语义键，两者不可互替。(c) **确定性判定要拒绝混合证据，签名要覆盖全部可能改变行为的维度**——hermes-agent 的 `deterministic_empty` 要求 `all(a.signature == first.signature)`（`signature = (model, provider, finish_reason)`，**含 provider 不是只含 model**）且 `all(usage_present and zero_output)` 或 `all(无 usage 且无观测到的生成)`，**混合证据（一部分有 usage、一部分没有）fail open 保留完整重试预算**，docstring 写明「Mixed evidence fails open so ambiguous transients keep their retries」。两处都要判：用 `any` 而不是 `all` 会把「一次真空 + 一次巧合」当成确定性，提前放弃重试；签名漏掉 provider 维度会让「同模型名不同网关」的两种失效被当成同一个。fail-open 的代价要写出来（这里写在注释里），不然审计无法区分「保守方向的 fail-open」与「漏配」 |
| **M12** | 输出契约校验：响应是否通过结构化 schema 校验 | agent 自由文本输出直接喂给下游解析，解析失败静默降级 → **正向判据：「解析失败怎么办」必须是三个可区分分支**——重试、升级为失败、还是降级？降级时有没有发出「已经降级」的可观测信号？没有信号的静默降级把契约违约变成了成功返回，和 M7/M10 是同一类形态。**另要问判据本身可判定吗**：如果「是否符合契约」由模型自判（自评输出是否合格），就退化成「让作者批改自己的作业」，这条防线没有强制力，等同 X3 的交接条件由模型自判 |
| **M13** | 安全护栏：prompt injection（内容来自外部/爬取）、输出泄露、PII 处理、工具权限边界 | 爬取内容直接进 prompt 无净化；工具无权限分级，低权限 agent 可触达高权限工具 → **正向判据：「有分类」不等于「覆盖完整」，三步问**——(1) 分类有哪些取值？(2) **哪些代码路径跳过分类、走了默认值？**（委派工具、外部/MCP 工具被硬编码成只读是两条经典旁路）(3) 默认值在权限模型里代表什么？只要存在走默认值的路径，判 `RISK` 而非 `OK`。另：**审批必须 fail-closed**——观察通道的容错（错误隔离、静默降级）用在准入通道上，等于「审批服务挂了 = 全部放行」。**第三条问：这条防线能不能物理阻止被禁止的动作？** 建议性约束（提醒、协作式超时、注入上下文让模型自己改）降低失败概率，但不让失败不可能。deepseek-harness 的 `packages/guard/` 全线自述为 advisory——`timeout-policy` 是「Cooperative, never a hard kill」，且内建的 `bash`/`read`/`write`/`edit` 均未声明 `timeoutMs`，即**默认无时限**；`repeat-tool-reminder` 是「Advisory, not veto. It never blocks or rewrites a call.」它的强制层是另一个独立包（`interaction/user-approval/`，fail-closed）。准入条件：**唯一的安全边界如果是建议性的，判 `RISK` 而非 `OK`**；同时问「默认配置下强制层启没启用」——需要显式配置且无注册表默认值的护栏，等于没有护栏。**再加一问求值顺序**：存在不可被配置覆盖的硬拒层时，看它排在所有可配置项之前还是之后——`FULL_AUTO`（全放行）分支如果放在敏感路径检查之前，那条硬拒层就形同虚设。求值顺序是实质，不是细节：同样一份名单，顺序错了就从安全边界变成摆设。**第四条问：fail 方向要按通道逐条声明，不是按项目统一选。** hermes-agent 的护栏全线 fail-open——每个 stop gate 的配置查找都包在 try/except 里，异常时返回 None，该 gate 静默失效；成本护栏明确「unknown pricing 时不触发」；`empty_response_guard` 的 docstring 直接写着「Both guards fail OPEN to legacy behaviour」。这不是缺陷本身，而是**方向必须逐条写出来**：准入通道 fail-open 等于「护栏服务挂了 = 全部放行」，观察/降本通道 fail-open 等于「宁可不省钱也不误伤任务」。审计能区分「设计选择」和「漏了」的唯一依据是那条通道有没有声明自己的方向；声明缺失的 fail-open 一律判 `RISK`，因为从外部看它与漏配无法区分 |
| **M14** | 模型不确定性：随机种子 / 温度是否记录、`temperature>0` 时是否假设了确定性输出 | 温度 0.7 却假设输出可复现 → **正向判据：区分「假设确定性」和「记录不确定性」两个动作**。前者是设计选择，后者是审计义务：哪怕温度非零、注定不可复现，模型名 / 温度 / 采样参数也要落盘——否则出问题时连「当时用的是什么」都答不上来，X2 的可重放无从谈起。审计问法是「这个项目哪一行断言了输出可复现？」（缓存键、去重键、幂等键、结果比对），答不上来但存在这类断言，判 `GAP`；答得上来且参数已记录，判 `OK` |

| ID | 检查什么 | 常见漏点 |
|---|---|---|
| **L1** | 外层编排循环边界：外层迭代上限 + 明确终止条件 | 外层无上限，靠「模型会自己停」→ **正向判据：终态必须是代码里可区分的三条路径**（正常完成 / 达上限熔断 / 无节点 ready 判为卡住），不能靠一个布尔量事后推断。收缩类逻辑（skip、timeout 收敛）必须有前置条件——只有「本波次真的没人在跑」时才收缩，否则会把等回边的节点误判成死节点。**两条追加判据**：(a) 还要问第四问——如果这个循环**根本没设上限**，退出时能被观测到吗？`while` 理论上永不退出，所以「未达上限就退出」本身是异常事件，必须有它自己的终态名字；混在同一个错误里，修复建议就没法定位（达上限了 = 降轮数；压根没配上限 = M1 的 GAP）。(b) 基于信号/事件唤醒的循环，**唤醒可被丢弃**（非阻塞发送、有界队列溢出）时必须有有限轮询兜底——否则丢信号是活性 bug：任务永远不会被调度且无错误可查。审计时问「唤醒能不能丢」，答「不能丢」但发送是非阻塞的，就是声明与实现不一致。**第三条追加判据：终态字段有默认值就等于没有，要按「有多少条路径被赋予了名字」来数。** hermes-agent 有两个同名字段：模块内诊断用的 `_turn_exit_reason`（注释写着 `# diagnostic: why the loop ended`，默认 `"unknown"`）与结果契约字段 `turn_exit_reason`。在取回的 18 个文件里前者只赋值 1 处、后者只赋值 3 处（均为上下文压缩超时类终态），而可识别的终止路径有 15 条左右——只有 3 条路径带得上名字，其余在观测面看起来完全一样（都是默认值）。只看「有没有这个字段」会被默认值蒙过，只看「有没有赋值」也会被「有 2 处赋值」蒙过。判据问法：**先数出终止路径总数，再数出被赋值的路径数，报比例**——比例低于三分之一时，观测面上根本分不清是哪条路径退出的，L1 的第一条判据（三条路径可区分）不成立，尽管代码里每条路径都写了 `return`；低于一半时判 `RISK`（见 `references/loop-engineering-patterns.md` 模式 52 的两档阈值）。**同构的另一半是「授权点不在本模块」**：hermes-agent 的主循环条件里出现 `agent._budget_grace_call` 作为豁免项，但它在整个 loop 模块内从未被写入——被预算守卫放行的例外通道，其授权点不在 loop 自己的源码里。审计从 loop 侧无法判断这个豁免谁能开、开了多久；这种「条件里引用了本模块不拥有的状态」的形态，和缺失守卫同样严重，因为豁免比无守卫更难审计：无守卫是明面上的缺口，不可审计的豁免是看不见的缺口 |
| **L2** | 预算下传：总预算是否传递到每个子 Agent？子 Agent 是否独立受限？ | 外层设了上限、内层无上限 = 白设，这是最普遍的宏观漏洞。**但「是否继承」逐框架不同**：OpenAI Agents SDK 的 handoff 共享 run 级 `max_turns`（继承成立）；LangGraph 子图需显式传递；ADK 的 `max_iterations` 只管 LoopAgent 自己的迭代、子 agent 终止靠各自的 `tool_context.actions.escalate` → **正向判据：要有 Run 树级的聚合预算**，而不只是每层各自的局部上限。局部上限之和没有上界时，深度守卫再严也拦不住烧钱。另：**除了问「有没有下传」，还要问「每一条构造路径都接上了吗」**——上层包装器构造引擎时漏传上限参数、落回默认值，是这道检查最容易漏掉的形态：它不是「配置错了」，是那条路径**根本没接到配置**，所以配置审计看不出来。**第四条：必须写出来「预算是 per-agent 还是 run-tree 聚合」，且写出来的方向要能被算术反查。** hermes-agent 的 `IterationBudget` 把这件事写成了文档而不是代码：父 agent 上限 500，每个子 agent 上限由 `delegation.max_iterations` 默认 50 控制，文档明说「因此 parent 加所有 subagents 的总迭代数可以超过父 agent 上限」——**这是设计意图，不是漏配**。局部上限之和没有上界，与上面「局部上限之和没有上界时深度守卫拦不住烧钱」是同一个缺口，但它的形态不同：不是「忘了配聚合预算」，而是「明确拒绝聚合并声明了为什么」。判据因此要分两档记：漏配 = `GAP`；显式声明不做聚合、并写出总消耗的上界（或明确写出「不设上界」）= `RISK`，但要能引用到声明的那句话。两档的区别在于修复成本：漏配要补代码，显式声明要补一个跨层总闸或补成本维度兜底（见 M1），审计建议必须落到具体那一条 |
| **L3** | 委派深度与广度：递归深度上限 + 每层子 Agent 数量上限 | 子 agent 递归调用子 agent，深度无界 → **正向判据：深度与广度必须分别问、分别判**。深度有守卫不等于 L3 通过——一次 fan-out 一万个副本，一万个节点同一波次 ready、每个各调一次模型，深度有界而广度无界。广度上限缺失时的正确修法是**抛异常而不是截断**（截断 = 静默丢任务）。另：**并发与限流守卫要排除「已经在跑的工作」与「自身」**——harness/harness 的 `withinLimits` 显式排除了其他仓库、自己、其他名字，`shouldThrottle` 对 `CIStatusRunning` 直接返回 false。这两处排除不是巧合：守卫如果追溯已在执行的任务，就是自我锁死；如果把自己算进计数，一次调度就会把自己限流掉。审计并发守卫时问「这个计数里包不包括当前这次？」，答「包括」就要判 `RISK` |
| **L4** | 外层决策可判定性：continue / retry / fix / escalate 四态是否都是可机器判定的条件 | 「决定继续」依赖模型自判 → 无法收敛 → **正向判据：分支条件必须是可机器判定的**；必须由模型判定的（如「是否达成共识」）要显式标出来并单独判 `RISK`。另：**回到某个节点的操作必须显式区分「立即释放」与「等入边就绪」**——迭代收敛点用立即释放会读到空状态，然后「合成了一个空结果」，这是不报错的错误。**追加一问：fan-out 之后谁是裁判？** 把多个模型的结果拼成编号块交给聚合者时，聚合者是谁、它能看到什么，要能一句话答出来。hermes-agent 的 MoA loop 是 reference model 当上下文提供者、**聚合者是主模型的下一次调用**（`owns tool calling and turn termination`）——reference 的输出不进入终止判据，所以 L1「终止条件可区分」在 fan-out 后仍然成立。反面形态是「裁判也是一个 LLM、且它能不能判取决于另一个 LLM」，那终止条件就不可机器判定了，整条 L4 的判据链断掉。判据：**写出聚合者的名字，并确认它的输出不进入终止判据** |
| **L5** | 检查点与恢复：状态快照是否存在？恢复时不丢状态、不重复副作用 | 有检查点但恢复会重放已完成的副作用（重复下单、重复发送）→ **正向判据：检查点对象里不能有活对象**（client、session、connection）。把「连线」和「数据」拆成两个类型，检查点自动变干净；混在一起时靠序列化白名单是漏的。**三条追加判据**：(a) **收尾路径不能继承触发它的那个取消令牌**——取消流程本身是被取消的那个操作的一部分，如果收尾绑定同一个 ctx，被取消的操作连自己的清理都做不完（harness/harness 的 teardown 对所有存储 I/O 用 `noContext`，只在下游调度/取消/上报用 ctx，就是这个理由）。(b) **检查点要显式记录「续跑什么」，而不只是「跑到哪」**——pi 的 checkpoint 带 `continuation: { kind: "need_assistant", overflowRecoveryUsed: false }` 与 `triggerEntryId`，恢复时是 `kind: "resume_checkpoint"`。只存状态不存意图，恢复方就得猜下一步，猜错是无声的。(c) **检查点必须是操作（状态转移），不是对象**——pi 的 `CheckpointOperation` 是带 `at: "checkpoint"` 的日志条目，落进 session 日志本身，所以检查点是事件溯源的一部分，不是旁路的对象存储。**三条追加判据**：(a) **对外部资源执行破坏性操作时，删除授权要绑定到用户在确认时看到的那一批身份，不要重扫**——hermes-agent 的 checkpoint prune 在交互确认后把 orphan 集合冻结成 `orphan_allowlist`，后续扫描即使发现新的 orphan 也不会删；注释明确写「一个在预览之后才变成 orphan 的项目（等待 input() 期间 workdir 消失）不能被顺手扫进去」，并且「空预览绑定空 allowlist，所以它永远无法授权后来扫描到的 orphan」。**空集也要无条件设置，这个细节是关键**：只在「有 orphan 时」设置 allowlist 会让「预览时没有、确认时有」的路径绕过绑定，而这条路径正是 TOCTOU 的入口。(b) **区分「资源不存在」和「资源暂时不可达」**——同一段代码里 `workdir` 不可达既可能是项目被删了，也可能是网络卷 / VPN 掉了；后者在 prune 里被当成 orphan 删除就是灾难。hermes-agent 把这两种可能直接写进确认提示（"A workdir can be unreachable because the project was deleted, or because an external volume / network share / VPN is down."），并提供 `--keep-orphans` 走只删 stale 的窄路径。判据：**任何「不可达」类信号在驱动删除时都要有窄化开关**，否则一次网络故障等于一次批量删除。(c) **观察型报告与已提交的报告要分成两次发布，措辞要匹配**——hermes-agent 的 liveness 看门狗在真正提交 abort 之前只发布「检测到停滞、正在尝试恢复」，注释写着「Pre-commit surface is OBSERVATIONAL only… must not claim the abort or the lease withdrawal has committed — the next operation can still veto the outcome」；确认性的措辞只在 `_commit_abort` 成功且租约关闭之后发布。这是 L6「终态要能区分」在用户可见报告上的同源要求：**报告比实际状态超前一句，就是让用户以为有兜底而实际上没有**，出问题时用户不会重跑、也不会去查日志 |
| **L6** | 副作用幂等与去重：外部副作用（支付、发消息、写库）是否有幂等键 | L5 恢复 / L7 重试触发重复副作用 → **正向判据：三步问，三步都答得上才算 `OK`**——(1) 有没有键？(2) **键的粒度是操作级还是更粗？**（节点级/attempt 级的键会让同一波内的多个调用碰撞）(3) 谁在读这个键、有没有强制去重？只答上第 (1) 步是最常见的误判：键存在、被文档化了、但会碰撞且无人强制，比没有键更危险——错误的去重让操作**静默丢失**而不是报错。**两条追加判据**：(a) **部分失败必须编码进数据，不能只进日志**——harness/harness 的 teardown 把 sibling 状态折成 execution 状态（Killed → Failure → Error，首个匹配胜出），取消器给被杀的 step 写 `ExitCode = 130`、给未启动的写 `Skipped`。日志里写「有个 step 失败了」对下游没用，下游要读到的是「这个 step 从来没跑过」。(b) **终态要能区分「启动后被杀」和「从未启动」**——同一个 `Failed` 覆盖两种情况，下游就没法判断要不要重跑（重跑已跑过的 = 重复副作用；不重跑没跑过的 = 任务丢失）。这个区分比幂等键更靠前，因为幂等键只在「会重跑」时才起作用。**两条追加判据**：(a) **部分失败的编码方式要可配置，且判据看默认方向**——harness/harness 的编码是强制的（下游必须读到结构化状态），hermes-agent 的 MoA fan-out 把它做成了策略开关 `degraded_reference_policy`，取值 `loud` / `silent`，**默认 `loud`**：失败的 reference 从上下文里过滤掉，同时把 `[Reference models unavailable: labels]` 追加进聚合者能看到的输入，让它知道自己在少样本条件下做判断。两个方向都有实现，但默认是 loud 这一条本身就是判据——「能不能静默」是能力，「默认是否静默」是设计选择，审计要判后者。默认 silent 的部分失败等于把「聚合器在降级条件下工作」伪装成「聚合器正常工作」，与 L10 的「证据缺失时判过」同构。(b) **失败的槽位不能污染统计口径**——`_sum_reference_accounting` 按每个 advisor 自己的费率汇总，失败槽位只参与计数不参与计价；混进计价的分母会让「这次更贵」和「这次少一个人干活」混成同一个信号，成本告警就失去定位能力。部分失败同理要问报告的措辞层级：失败槽位被过滤掉时，聚合者看到的是「证据变少」还是「一切正常」，两者要能区分——见 L5(c) 的观察型/已提交分两次发布（同一要求落在用户可见报告上） |
| **L7** | 失败收敛策略：换参数 / 换 agent / 升级人工 / fail-fast 的路径是否定义 | 只有「再试一次」，没有「试到第几次做什么」→ **正向判据：两级错误策略，按「谁能修好它」分类**——模型能修的（缺参数、工具抛异常）转成数据回传给模型；模型修不了的（结构性错误）必须 fail-fast 并响亮。分类依据**不能是异常类型**（`ValueError` 有时该重试有时不该）。配套：**超限绝不合成答案**，宁可直接失败也不产出「看起来完成」的东西 |
| **L8** | 重试策略与退避：即时重试 vs backoff + jitter；重试是否换了参数 | 相同输入即时重试 = 同样地失败 N 次，纯烧钱 → **正向判据：五问，缺一问就不能判 `OK`**——(1) 有没有最大重试次数？(2) **可重试错误码是不是白名单**（不是 `except Exception`）？(3) 延迟有没有上限？(4) 有没有 jitter？(5) jitter 是乘性对称还是加性？（纯指数无 jitter 会让并发重试同步齐步，形成 thundering herd）另有三条硬要求：**重试判据要可替换**（谓词或策略对象，不是硬编码 if-else）；**默认值必须保守**——`retry_on=(Exception,)` 这种默认把「重试策略」变成了「所有错误都重试」，会把程序 bug 也重试掉；**指数要防溢出**（`2 ** retry` 在 `retry` 极大时会让延迟算成天文数字）。机制和默认值**必须一起判**：策略对象设计得再好，默认 `retry_on=(Exception,)` 仍然零分（案例 1 的形态）；反之默认值有上限但判据硬编码，用户无法收窄重试范围。**两条来自上游的追加判据**：(a) **双正则分类时，非重试的必须在重试的之前测**——pi 先测 `NON_RETRYABLE_PROVIDER_LIMIT_ERROR_PATTERN` 再测 `RETRYABLE_PROVIDER_ERROR_PATTERN`。反向顺序时，一个同时匹配两者的错误串（限流消息里常常含 retry 字样）会被判成可重试，限流就被重试探满预算。(b) **溢出要防两层，不是两层里挑一层**——JS 里 `Number.isSafeInteger` 兜的是数值精度，`setTimeout` 的 32 位上限要单独 `Math.min(remaining, 2_147_483_647)`。只防其一的形态：延迟算出来正确但 `setTimeout` 拿到天文数字直接静默不触发，重试永远不回来。**两条追加判据**：(a) **上限和退避表要一起算，算式要写出循环退出条件的顺序**——hermes-agent 的 `zai_coding_overload_retry_ceiling = short_attempts + len(long_backoff_table) + 1`，注释明确写「循环在计算本次退避**之前**判断 `retry_count >= ceiling` 放弃」。+1 不是随手加的安全余量，是从循环的判断顺序反推出来的：如果上限等于表长，最后一档退避永远不会被用上。审计重试表时不要只看「有没有上限」，要看上限能不能取到表里的每一档；取不到最后一档的上限，等于表尾配置了但永远不会执行。(b) **jitter 的随机源在粗时钟或并发下必须额外去相关**——纯时间戳做种子，多个并发会话在同一毫秒内拿到同一个种子，退避完全同步，thundering herd 原样回来。hermes-agent 用 `time.time_ns() ^ (tick * 0x9E3779B9)` 配合一个加锁的单调计数器，注释写「so coarse clocks still decorrelate」——它是在防「时钟不够细」这一种，不是只防「固定种子」。(c) **被多处消费的同一常量要单一来源**——hermes-agent 的短重试次数由 `adaptive_rate_limit_backoff` 与 `zai_coding_overload_retry_ceiling` 共用同一个模块常量，注释写「the two cannot silently desync」。同一个数字写在两处时，改一处忘改另一处不会报错，只会让退避表和上限永久不一致 |
| **L9** | 跨 Agent 结果一致性：冲突检测 + 事实单一来源 | 两个子 agent 给出矛盾结论，外层直接拼接 → **正向判据：先问「有没有一个字段是事实唯一来源」**。有唯一来源时，其他 agent 的结论只是引用而非新增事实，冲突在构造期就不可能出现。没有唯一来源就要问冲突怎么发现——拼接式合成（把两份结论写进同一个回复）不产生任何可检测的冲突信号，它只是让两个矛盾事实同时为真。判定条件：**如果两份结论互相矛盾，代码里有没有一个分支会因为这个矛盾而停下来？** 答不上来判 `GAP`。注意这不是「加个 LLM 去比对」——让模型判冲突又退回到 M12 那个「让作者批改自己的作业」形态 |
| **L10** | 验收与 Goodhart 防护：done 判据 + 边界条件（「不许做什么」），验收器不可被被优化对象修改 | 只用「所有测试通过」做出口 → agent 删测试就赢了 → **正向判据：fail-fast 之外还要有「挂起等人工」这条路**。重试耗尽后当前只能抛异常，等于「要么无限重试要么直接死」，缺了中间那档。**Goodhart 的具体形态：验收器在「证据缺失」时判过**。OpenHarness 的 `_wait_for_pr_ci` 在 `no_checks_grace_seconds` 之后如果仍然没有收到任何 remote check，返回 `("success", "No remote checks were reported after the grace period.")`——验收器在检查项根本不存在时给出通过结论。审计验收逻辑时必须问「没有证据时算什么结果？」，答「超时算通过」就是这一档。同构形态还有：检查项集合为空 → 判全绿；验收脚本自己被删 → 判没有失败项。这类缺陷比「验收标准太松」更隐蔽，因为它有完整的超时、优雅等待、快照机制，看上去是严谨的实现 |

## 跨层（5 项）

| ID | 检查什么 | 漏点 |
|---|---|---|
| **X1** | 可观测性：每次迭代是否有结构化日志（迭代号、成本、决策、工具调用、错误） | 只有最终结果日志，中间决策链不可追溯 → **正向判据：日志要能回答「这次花了多少」和「哪个工具调用坏的」**。事件里有重试次数、延迟、错误类型但没有成本、token、工具名与参数时，仍然无法定位根因——重试元数据不是成本观测。**可观测性还要过两道关：观测面能不能被审计，以及原始输入能不能不进观测面。** hermes-agent 的 `ToolCallSignature` 把工具名与规范化参数做成 `sha256(canonical_tool_args(args))`，注释写「Stable, non-reversible identity」，而 `to_metadata()` 只导出哈希——「Return public metadata without raw argument values」。这是把「去重要能比较」和「日志要能给人看」分成两个动作：内部用哈希去重（可比较、不可逆），对外只暴露哈希（可引用、不可还原）。判据问两点：(1) 观测面里有没有出现只在内部需要的原始输入？出现了就要区分「必须留证」和「顺手记了」——后者要么脱敏要么删。(2) **观测面的分类逻辑要和执行面的分类逻辑共用同一个函数**——hermes-agent 的 `classify_tool_failure` 注释写「mirrors `agent.display._detect_tool_failure` so the guardrail never disagrees with the CLI's `[error]` tag」。两份各自实现的分类器会在边界值上分叉，用户在日志里看到「这一步是警告」而实际执行时它已经被当成失败，观测面与执行面不一致的失败比观测缺失更坏，因为它给出的是错的安慰 |
| **X2** | 可重放：随机种子 / 时间戳 / 外部响应是否被记录 | 出问题后无法复现 → **正向判据：区分「能重建状态」和「能重建运行」**。事件溯源存波次 delta 只能重建状态；模型的回复、模型名、温度没记录时，重放走一遍是另一条路径。这个区别在报告中要写明 |
| **X3** | 人机交接：升级人工的条件是否明确定义？交接信息是否完整？ | 无人工交接路径，或条件模糊（「模型不确定时」） → **正向判据：交接条件要机器可判定**。「何时问人」如果由模型自判，交接点就等于随机数；恢复时输入的形态（字典 vs 裸值）要有明确契约，靠启发式消歧是缺陷 |
| **X4** | 环境一致性：dev / staging / prod 的 loop 配置（上限、超时、模型）是否有差异 | 本地无限循环跑着挺好，生产有上限直接截断 → **正向判据：上限的缺失必须显式声明，且方向要单一反查得出来**。判定的核心不是「两个环境配置一样」，而是「哪个环境少了哪个上限」能在一处查出来：环境间差异表、或被引用的单一配置源。若每个环境各写一份完整配置，多出的那份永远不会被删，删的那份也无人知晓。审计问法：**把三个环境的上限配置并排，哪个环境在这一项上是空的？** 答不上来（因为差异分散在各处文件里）就是 `GAP`——X5 的空行在这里是配置层，在 X4 是环境层，两个都要判。**两条追加判据**：(a) **环境分层的差异要能在一处枚举出来，最好是一个字面量集合**。hermes-agent 的 `_ATTENDED_PLATFORMS = frozenset({"cli", "tui", "desktop", "acp", "subagent", "api_server"})` 把「有人在看」的环境定义成一个字面量集合，硬停止护栏在集合内默认关、集合外默认开（`hard_stop_enabled: False` 与 `non_interactive_hard_stop_enabled: True` 两个字段并列）。这是 X4 的理想形态：差异不是散在各处文件里，而是由一个集合的边界决定，审计要判断某个平台受不受保护，只需查它在不在集合里。集合本身也要判——**集合用的是包含式还是排除式**：`platform not in _ATTENDED_PLATFORMS` 意味着新加一个平台默认进入「受保护」侧（fail 到更安全的一侧），反过来写成 `platform in _UNATTENDED` 则新平台默认进入不保护侧。这个方向是设计选择，必须写出来。(b) **上限要按「是否受总开关控制」分层**。hermes-agent 的 `LoopCapConfig` 上限（50 次 web 搜索 / 50 个子 agent）注释明确写「fire regardless of `hard_stop_enabled`」，而普通护栏受该开关控制；`0` 是禁用某个 cap 的显式取值。这意味着「关掉硬停止」不会连带关掉资源上限——分层是刻意的，因为资源上限是防跑飞、硬停止是防失控，两者的受众不同（前者是运维口径，后者是交互口径）。判据：**列出所有上限后，逐个标注它受哪个开关控制，受总开关控制的上限有没有例外**；例外存在本身不是缺陷，例外不被写出来才是 |
| **X5** | 配置漂移：默认值是否静默失效？配置项拼错是否有警告？ | 配置 key 拼错一个字母 → 静默回落到无上限默认值 → **正向判据：枚举配置与数字配置分开判**。枚举做白名单校验（拼错即抛异常、错误信息带拼错的值）成本最低收益最高；数字配置要单独问有没有下限检查——`concurrency=0` 会让信号量永久锁死且无异常无日志，`max_waves=-1` 意味着完全无上限。一个项目可以在枚举上满分、在数字上零分。**三类校验分开问**：(1) 拼错的 key 会不会抛？(2) 数字越界会不会抛？(3) **字段之间有没有关系需要校验？** 第三类最容易漏——`headChars=5000`、`tailChars=4000`、`thresholdChars=8192` 三个值各自合法，加起来却超过阈值，裁剪器要么死循环要么输出比原文更长。跨字段不变量必须**在构造期**校验，留给运行期就是「出错后仍然成功返回」。deepseek-harness 的 pruner 这条校验写成了 `headChars + codePointLength(MARKER) + tailChars <= thresholdChars`，并且把解析出的配置 `deepFreeze(structuredClone(...))` 成深层不可变——**配置对象可变时，构造期校验等于没校验** **三类之外还有三类，见下方第四、五、六类**：第四类（配置是合并还是整体替换——省略即重置）、第五类（钳制必须可观测，且枚举值与数字值分开钳）、第六类（数字配置要主动拒绝会翻转控制流方向的值：NaN / Inf / 引号 bool）。判 X5 时这六类要一起问，答不上第四至第六类不算 `OK` |

**第四类：配置是合并还是整体替换？** 整体替换语义下，patch 作者漏写一个字段得到的是**默认值**而不是旧值。如果默认值恰好是无上限（deepseek-harness 的 `retry-policy` 省略即取 normal 默认 5 次重试，而 `always` 模式的 provider 省略即无重试上限），patch 会**静默移除**一条安全限制，且配置审计看不出来——这是「边界不可发现」在配置层的形态。审计分层配置时先问合并语义，再问漏写会发生什么。

**第五类：钳制必须可观测，且枚举值与数字值分开钳。** OpenHarness 的 `_safe_completion_token_cap` 对超限值做钳制后会通过 `StatusEvent` 报出「钳制了什么、钳到多少」。无声钳制让调用方以为配的是 20000、实际跑的是 8192，配置审计与运行行为长期不一致且无从发现。同时枚举型字段（如压缩级别）走白名单校验、数字型字段走范围钳制，两者不能共用一套处理，否则「拼错的枚举」会被当成越界数字静默回落到默认。

**第六类：数字配置要主动拒绝「会翻转控制流方向」的值，而不是只查越界。** hermes-agent 的 `_resolve_finite_seconds` 明确拦 NaN 与 Inf，理由写在 docstring 里：NaN 会通过 `> 0` 比较静默关掉超时，Inf 会让轮询循环卡在 `Event.wait`。这两个值都在「看起来是合法浮点数」的范围内，纯范围校验抓不到，但它们的破坏方式是**改变比较与等待的语义**，不是让数值变大。判据问法：**哪些配置值会让守卫从「在防」变成「没在防」，而不是让守卫更严？** 答不上来这类值清单的项目，数字配置校验只覆盖了一半——越界那半边（更大、更小、负数、零），翻转那半边（NaN、Inf、`null`、空字符串、类型错位）没人查。翻转类值比越界类值危险，因为它们通常不报错、不产生日志，只是让一个守卫安静地不再生效，形态上和「配错了 key 静默回落默认值」同源。同类形态还有一处更隐蔽的：hermes-agent 的 `resolve_guard_settings` 对 `enabled` 字段显式处理 YAML 把 `true`/`false` 解析成字符串的情况，因为 YAML 引号会让布尔变字符串，此时 `bool("false")` 是 True——**解析器对引号敏感的类型，必须自己处理字符串回落**，靠类型检查会把「关掉的护栏」读成「开着的护栏」 |
